You are wiring new public-domain artwork into the Collection of Beauty catalogue end-to-end. The user points you at raw material; you must end with new works appearing in `src/data/artworks.json` (and therefore on the site after they ff-merge the worktree branch).

## Input

Raw input from user: **$ARGUMENTS**

Interpret it in this order:

1. **Empty / "Downloads" / "look in Downloads"** → scan `~/Downloads` for image files (`.jpg .jpeg .png .tif .tiff .webp`) modified in the last 14 days. Show the list to the user before moving anything.
2. **Absolute or `~`-relative directory path** → treat as the source folder. List images inside.
3. **One or more Wikimedia Commons URLs** (`https://commons.wikimedia.org/wiki/File:...` or `https://upload.wikimedia.org/wikipedia/commons/...`) → download each to a scratch folder under `/tmp/ingest-<timestamp>/` with the exact Commons filename preserved (the fetch script keys on filename, so renaming breaks metadata lookup).
4. **Mixed** is fine — combine into one staged list.

If nothing usable, ask for clarification. Do not guess.

## Hard rules

- **Never rename Commons files.** `fetch-wikimedia-metadata.mjs` queries the API by exact filename. A renamed file gets zero metadata.
- **Never touch `assets-web/` by hand.** It is generated by `pnpm assets:shrink` from `assets/`. The dev server reads `src/data/*.json` which `build-data` regenerates.
- **Never edit `src/data/*.json` directly.** Always go through `build-data`.
- **Never delete a file from `~/Downloads`.** Move with `mv` only after the user has confirmed the bucket. If user said "copy", use `cp`.
- **Do not open a PR.** Commit on the worktree branch, ff-merge into main, then stop.
- `pnpm assets:sync` runs automatically after build-data succeeds. The script is dotenvx-gated on `.env.production` + `.env.local`; if those are missing it errors with a clear message — surface that to the user and proceed with the rest, do not retry.
- After commit, rebase this worktree onto main and ff-merge into main so the dev server picks up the new data. The dev server runs from the main worktree, not this one — until the merge lands the new artworks are invisible in the browser. Use `git -C <main-worktree-abs-path>` for any command against the main checkout; bash `cwd` resets between calls and bare `git` would target the wrong worktree.

## Step 0 — Verify the worktree is clean enough to commit

```bash
git status --short
```

If there are unrelated dirty files in the worktree, stop and ask before continuing. Ingest produces large diffs in `metadata/` and `src/data/` — you do not want to commingle.

## Step 1 — Discover candidates

`~/Downloads` is a junk drawer. The default scan must aggressively reject personal photos, screenshots, non-Wikimedia downloads, and Wikimedia downloads that aren't art. False positives waste polite-API calls and ship logos as art; false negatives are recoverable (user can pass an explicit path). Bias toward rejection.

### 1a. Extension + recency

```bash
find ~/Downloads -maxdepth 1 -type f \
  \( -iname '*.jpg' -o -iname '*.jpeg' -o -iname '*.png' \
     -o -iname '*.tif' -o -iname '*.tiff' -o -iname '*.webp' \) \
  -mtime -14 -print
```

### 1b. Filename blacklist (drop screenshots + obvious non-art)

Drop any path whose basename matches (case-insensitive):

- `^(IMG|DSC|DSCN|DSCF|PXL|MVIMG|HEIC)_` — camera-roll patterns
- `^Screen ?Shot|^Screenshot[ _]` — macOS / Windows screenshots
- `^Photo on \d` — Photo Booth output
- `^WhatsApp `, `^Signal-`, `^IMG-\d{8}-WA` — messenger exports
- `^CleanShot|^Snip|^Capture`, `\.HEIC$` — capture tools and iPhone formats
- `^Flag_of_|^Coat_of_arms_|^Seal_of_|^Map_of_|^Logo_of_|^Logo[-_]` — Commons categories that are not art
- `^Diagram[-_ ]|^Chart[-_ ]|^Graph[-_ ]` — informational graphics

### 1c. macOS provenance via xattr

Safari, Chrome, Firefox, and most browsers stamp downloaded files with `com.apple.metadata:kMDItemWhereFroms` (a binary plist holding the source URL). Read it:

```bash
xattr -p com.apple.metadata:kMDItemWhereFroms "<file>" 2>/dev/null \
  | xxd -r -p \
  | plutil -convert json -o - - 2>/dev/null
```

Classify each survivor of 1a/1b into one of:

- **`wikimedia`** — origin URL contains `wikimedia.org` or `wikipedia.org`. Keep.
- **`artsource`** — origin URL contains `metmuseum.org`, `rijksmuseum.nl`, `nga.gov`, `getty.edu`, `nypl.org`, `wellcomecollection.org`, `loc.gov`, `si.edu`, `archive.org`. Keep but flag — these need a different metadata path (Wikimedia API won't know about them; see failure modes).
- **`other-url`** — has a download origin but it's not on either list above. Drop by default; show the URL in the report so the user can override.
- **`no-origin`** — xattr missing entirely. Could be AirDrop, USB transfer, generated, or copied via Terminal. Default: drop. Exception: if the filename matches a Wikimedia Commons title pattern (contains underscores in title-case words and ends with a real extension, e.g. `Hokusai_Great_Wave.jpg`), keep but flag.

### 1d. EXIF camera-tag filter (defense in depth)

A personal photo without a download xattr can slip through 1c. Reject if the file has camera-make EXIF:

```bash
exiftool -s -s -s -Make -Model -Software "<file>" 2>/dev/null
```

If `Make` is a known camera vendor (Canon, Nikon, Sony, Apple, Samsung, Google, Fujifilm, Olympus, Panasonic, Leica, GoPro, DJI) AND `Software` does not contain `Wikimedia`, `Commons`, `MediaWiki`, drop the file. Museum scans usually carry scanner make (Epson, Phase One, Hasselblad with `H6D-...`) — keep those.

If `exiftool` is not installed, fall back to a `sips -g make -g model` probe on macOS:

```bash
sips -g make -g model "<file>" 2>/dev/null
```

Skip this stage entirely if neither tool is available; rely on 1c.

### 1e. Show staged list + categorize

Output one row per surviving file:

```
KEEP   wikimedia    Hokusai_Great_Wave.jpg                3.4 MB    https://commons.wikimedia.org/wiki/File:...
KEEP*  artsource    DP-19453-001.jpg                      8.1 MB    https://www.metmuseum.org/art/collection/...  (non-Wikimedia, manual metadata needed)
DROP   filename     IMG_4521.HEIC                         2.0 MB    (camera-roll pattern)
DROP   no-origin    cat-meme.png                          0.4 MB    (no download xattr, no EXIF Commons marker)
DROP   blacklist    Flag_of_Brazil.svg                    0.1 MB    (filename blacklist)
DROP   other-url    pinterest-image.jpg                   0.8 MB    (origin: pinterest.com)
```

Print totals: `N kept, M dropped (by reason: …)`.

Ask the user one question before moving: **"Proceed with N files? Reply yes / or list filenames to flip KEEP↔DROP."** Default no on empty reply. Do **not** move anything yet.

### 1f. Commons URLs (when input is URLs, not a folder)

For Commons URLs, the canonical download URL is `https://commons.wikimedia.org/wiki/Special:FilePath/<filename>` which 302s to the latest revision. Use `curl -L --user-agent "CollectionOfBeautyIngest/1.0 (personal)" -o "<filename>" "<url>"` with a small per-request delay (≥250ms). URL-supplied files skip stages 1b–1d (the URL itself is the provenance).

### 1g. Post-fetch art classifier

Even after 1a–1e, a Wikimedia download can be a map, a graph, a coin, a building photograph, or a contemporary photograph that happens to be PD. Run this check **after** `scrape:fetch` (Step 5) but **before** `assets:shrink` (Step 7):

```bash
jq -c '.[] | {file, categories: (.categories // [])}' metadata/<bucket>.json \
  | grep -iE '"(Maps|Flags|Coats of arms|Logos|Diagrams|Charts|Graphs|Screenshots|Coins|Banknotes|Stamps|Buildings of|Photographs of buildings|Aerial photographs)"' \
  | jq -r .file
```

Surface the resulting filenames to the user as **"likely not art — drop?"** with a yes/no gate. Move dropped files to `assets/.rejected/<bucket>/` (not deleted — the user may overrule later) and remove their entries from `metadata/<bucket>.json` before shrinking.

This stage is heuristic, not exhaustive. The user has the final say.

## Step 2 — Pick the bucket

Each artwork lives under `assets/<folder>/<filename>`. The folder groups by source/collection, not by artist. Existing folders:

```bash
ls -d assets/*/ 2>/dev/null
```

Decide bucket:

- If every new file looks like it belongs in an existing bucket (e.g. all Audubon plates → `audubon-birds`), propose that.
- If the material is a coherent new source (e.g. "ukiyo-e from the British Museum"), propose a new kebab-case folder name.
- If the material is mixed, propose splitting into multiple buckets and process each in turn.

**Ask the user to confirm the bucket(s)** before moving anything. This is a one-question gate, not a multi-step discussion.

## Step 3 — Filename collision check

Before moving, check for collisions inside the target bucket and across all buckets (build-data slugifies `<folder>-<filename>` for the id, so cross-bucket dupes get unique ids but the file content is wasted disk):

```bash
# in-bucket collisions
for f in <staged files>; do
  test -e "assets/<bucket>/$(basename "$f")" && echo "COLLIDE: $f"
done

# cross-bucket exact filename match (informational — different folder = different id)
basename "$f" | xargs -I{} find assets -name {}
```

If an in-bucket collision exists with identical bytes (`cmp -s`), drop the staged copy. If bytes differ, ask the user — do not auto-resolve.

## Step 4 — Move into `assets/<bucket>/`

```bash
mkdir -p assets/<bucket>
mv <source> assets/<bucket>/<filename>   # or cp if user said "copy"
```

Record the list of new filenames — you will use it in the report.

## Step 5 — Fetch metadata

```bash
pnpm scrape:fetch <bucket>
```

This queries Wikimedia Commons for every file in `assets/<bucket>/`, caches per-batch responses under `metadata/.cache/<bucket>/`, and writes `metadata/<bucket>.json`. It is polite (maxlag=5, single-threaded, 250ms between batches), cached, and idempotent — files already fetched are skipped via the cache.

If a new bucket is being created, this step also creates the metadata file. If the bucket folder exists but is not in the default normalize list (`collection-of-beauty.json`, `audubon-birds.json`, `kunstformen-images.json`), pass the explicit filename to the normalize step.

## Step 6 — Normalize metadata

```bash
node scripts/normalize-metadata.mjs <bucket>.json
```

This cleans QuickStatement markup, re-extracts years from Wikidata creation dates instead of EXIF upload dates, and writes `metadata/needs_review_dates.txt` for entries dated ≥1926 (copyright cutoff). Read that file and surface any new entries in the final report.

## Step 7 — Shrink

```bash
pnpm assets:shrink --folder=<bucket>
```

Skips sources whose variants are already current. For new files this builds 8 AVIF + 1 WebP per source, plus an extra full-resolution AVIF if the source is over 4096 px wide. Expect ~10s–60s per source on a typical Wikimedia scan.

## Step 8 — Fetch provenance (optional, slow)

```bash
pnpm scrape:provenance
```

Adds Wikidata links and museum/collection info. Network-bound, polite, idempotent — only fetches ids not already in `metadata/provenance.json`. Run it; if it errors or takes more than a couple of minutes, skip and note in the report that provenance can be backfilled later.

## Step 9 — Build data (first pass)

```bash
pnpm assets:build-data
```

Writes `src/data/{artworks,artists,movements,connections,summary}.json` from the merged metadata. Filters to entries with a source file present on disk, license = PD/CC0/CC-BY, and `!needs_review` flag. New artists not in `scripts/artists-db.json` get carried with no movement/born/died — capture those names for the report.

Step 10 needs this build to run first so curator-description generation can read the canonical artwork ids that build-data assigned (slugified `<folder>-<filename>`, sha1-suffixed on collision).

## Step 10 — Generate curator descriptions

Every new artwork gets a 2–3 sentence curator description written into `metadata/curator-descriptions.json`. This file already holds ~2,700 shipped entries — they are the corpus you mock voice from. The next `pnpm assets:build-data` run picks up the new entries and bakes them into `src/data/artworks.json` under each artwork's `description` field.

### 10a. Sample the corpus

Pull 30 random shipped descriptions across mixed buckets to refresh your sense of the voice. Bias toward non-Audubon entries (Audubon plates follow a tighter formula and overfit your output):

```bash
jq -r '
  to_entries
  | map(select(.key | startswith("audubon") | not))
  | sort_by(.key)[-200:]    # recent-ish
  | [.[range(0; length)]]
  | .[0:30]
  | .[]
  | "\(.key): \(.value)"
' metadata/curator-descriptions.json | shuf | head -30
```

If `shuf` is unavailable, drop it; the slice itself is varied enough.

### 10b. Voice rules (derived from the corpus, not invented)

The shipped descriptions follow a consistent shape. Match it exactly:

- **Length:** 2–3 sentences, ~200–320 characters total. Anything longer reads as essay; anything shorter as catalog stub.
- **Structure:** sentence one describes what is in the picture. Sentence two adds one verifiable technical or historical fact (medium, technique, date of execution, exhibition history, sitter identity, named series, plate number, named patron). Sentence three (optional) connects to the artist's practice in one concrete clause.
- **Concrete nouns.** Name the pigment, the plate technique, the support (panel, copper, linen), the patron, the city, the year. No "this striking work depicts…"
- **No interpretation.** No "becomes about", "speaks to", "asks us to", "captures the essence of", "evokes", "embodies", "renders the soul of". Describe surface and document fact; let juxtaposition do the rest.
- **No hype.** Banned: stunning, breathtaking, must-see, iconic, masterpiece, haunting, evocative, striking, powerful, captivating, the future of.
- **No anthropomorphism of weather/light/time.** Dusk does not "settle"; light is not "tender"; silence is not "loud".
- **No tricolons.** Three-item rhythmic lists are the loudest LLM tell. Use two items, four, or a single observation. ✗ "Plate captures the bird, the foliage, the morning light."
- **No em-dashes.** Use commas, periods, semicolons, parentheses, or rewrite. Compound-modifier hyphens (`shin-hanga`, `off-centre`) are fine.
- **No collective opener.** Don't start with "This work…", "The painting…", "An exquisite study of…". Start with a concrete noun from the picture itself or with the plate/series identifier ("Plate 23 shows…", "A pair of…", "Hokusai's traveller…").
- **No meta closer.** Don't end with "remains a touchstone of…", "speaks to the artist's lifelong fascination with…". End on a documented fact or a concrete image.
- **Quote sparingly.** Direct quotes from artist letters are fine when sourced. Do not invent.

### 10c. Source facts from the web

For each new artwork that the user wants a description for, gather facts before writing:

1. The artwork's `description` field from `metadata/<bucket>.json` (often the original Wikimedia caption — usable raw material).
2. The artwork's `categories` and Wikidata id (if `metadata/provenance.json` has it) — the Wikidata item often lists collection, inventory number, medium, dimensions, dated event.
3. WebSearch for `"<title>" <artist> <year>` and, separately, for the Wikipedia page of the work. The English Wikipedia page for major works is the most reliable single source of one verifiable fact.
4. WebFetch the artist's Wikipedia page if the work itself has none; pull one fact about the period/series the work belongs to.

**Verifiability rule.** Every fact in the description must be traceable to (a) a museum collection page for the work, (b) a Wikipedia article whose source-citation you have actually read in the fetch result, (c) the Wikimedia file page's structured data, or (d) the artist's published correspondence. If a fact sounds too tidy (a romantic backstory, a one-line origin story) assume it's apocryphal and drop it.

If the web returns nothing usable, write a pure-description sentence about what's in the picture plus one technical fact from the Wikimedia metadata (medium, dimensions, support). Better short and true than long and embellished.

### 10d. Write entries in batches of 10

For each batch, draft 10 descriptions, then re-read each against the voice rules in 10b before writing the file. Specifically check, for every entry:

1. Em-dash anywhere? Replace.
2. Three-item rhythmic list? Cut to two or rewrite.
3. Opens with "This work…", "An exquisite…", "A stunning…"? Rewrite to open on a concrete noun.
4. Ends on a "speaks to / remains / captures" sentence? Cut that sentence.
5. Any banned hype word? Replace with the concrete observation that prompted the hype.
6. Anthropomorphism of weather/light/time? Replace with surface description.
7. Any fact you can't point to a source for? Cut.

Append entries to the existing `metadata/curator-descriptions.json` (preserve sort order: keys are sorted lexically in the file). Do not rewrite existing entries.

### 10e. Re-run build-data

```bash
pnpm assets:build-data
```

This second pass bakes the new descriptions into `src/data/artworks.json` so they are visible on `/artwork/[id]` and in the 3D gallery info card.

## Step 15 — Push variants to R2

```bash
pnpm assets:sync
```

`assets:sync` runs `bash scripts/sync-assets.sh` under dotenvx, which pushes `assets-web/` to the R2 bucket via rclone. It is idempotent — only changed files upload — but a fresh bucket of 9 variants × N new works is still a chunky upload. Let it finish.

Failure modes:

- **`.env.production` or `.env.local` missing** → dotenvx errors with a clear message. Surface to the user; the local catalogue still works (dev reads from `assets-web/` on disk), but the deployed site won't see the new variants until sync runs. Do not retry.
- **rclone not authenticated** → surface the error verbatim. Don't attempt `rclone config` from inside the skill.
- **R2 bucket rate-limited** → wait and retry once, then surface and continue.

If sync fails for any reason, continue to the merge step regardless. The catalogue commit is still useful on its own and the user can rerun `pnpm assets:sync` independently.

## Step 16 — Rebase worktree onto main, then ff-merge into main

Per the worktree workflow in CLAUDE.md: feature branches rebase onto main, then main fast-forwards onto the feature branch. Never a merge commit. The dev server runs from the main worktree, so the merge is what makes new artworks appear in the browser.

Determine the main worktree path (it is the repository's primary checkout, not the `.claude/worktrees/...` directory you are in):

```bash
git worktree list
# pick the entry whose path does NOT contain .claude/worktrees/
MAIN_WT=<that absolute path>
WT_BRANCH=$(git symbolic-ref --short HEAD)
```

Rebase the worktree branch onto the latest main:

```bash
git fetch origin main         # if origin is reachable; skip if offline
git rebase main               # from inside the worktree
```

If rebase hits conflicts, resolve them in place and `git rebase --continue`. Do **not** fall back to a merge commit.

Then ff-merge from the main worktree, handling any WIP there per the CLAUDE.md "ff-merge blocked by WIP" rule (stash → merge → pop):

```bash
# Check WIP in main worktree
DIRTY=$(git -C "$MAIN_WT" status --porcelain | wc -l | tr -d ' ')
if [ "$DIRTY" -gt 0 ]; then
  git -C "$MAIN_WT" stash push -u -m "WIP before ff-merge of $WT_BRANCH"
  STASHED=1
fi

git -C "$MAIN_WT" merge --ff-only "$WT_BRANCH"

if [ "${STASHED:-0}" = "1" ]; then
  git -C "$MAIN_WT" stash pop
  # If pop conflicts, resolve in place — preserve any improvements from
  # the ingest commit while keeping the WIP changes. Don't take one side blindly.
fi
```

If `merge --ff-only` fails, it means main has moved since the rebase — rebase again and retry. Never `git merge` without `--ff-only`.

The user's dev server (running from `$MAIN_WT`) will hot-reload `src/data/*.json` and the new artworks become visible.

## Failure modes to handle

- **`scrape:fetch` returns 0 hits** — the filenames probably aren't Commons titles. Surface this and ask the user where the metadata should come from. Do not proceed to shrink (we'd ship art with no attribution).
- **`artsource` files (Met / Rijksmuseum / NGA / etc.)** — Wikimedia API will return nothing. There is no automated fetcher for these in-repo. Surface them with their origin URLs and ask the user whether to (a) skip this batch, (b) hand-write entries into `metadata/non_wikimedia_sources.json` (existing file — follow its shape), or (c) re-upload to Commons first. Do not silently ingest them.
- **`shrink` runs out of memory** — pass `--concurrency=2` and retry. Some 700 MB Wikimedia scans push the bounded buffer hard.
- **`build-data` reports filtered-out works** — read its stderr; common reasons are missing license, missing source file, or `needs_review` flag. Each is a real problem; surface in the report and do not silently move on.
- **A Commons URL 404s** — title may have been renamed on Commons. Surface the URL; do not invent a fallback filename.
